# VI Telecom Sales & Customer-Care Copilot

A chatbot that helps VI (Vodafone Idea) care/sales reps answer **any** question
about the plans — grounded **only** on the VI plan dataset. It answers directly
and on-point, and if a fact isn't in the data it says so instead of guessing.

Built on **Google Gemini** (natural-language understanding) + **Streamlit**
(chat UI), on top of the clean wide dataset produced by `build_wide_dataset.py`.

## How it's grounded (no hallucination by design)

The catalogue is small (62 plans), so the **entire dataset is injected into the
model's context on every question** as the system instruction. The model is told
that JSON is its only source of truth — no vector DB / RAG to drift. It cannot
answer beyond what's in front of it, and replies *"That isn't in the dataset."*
when a fact is missing. It is also told to answer **concisely and on-point** —
exactly what was asked, no padded sales pitches or extra sections.

## Data source

The chatbot reads **`output/vi_plans_wide_dataset.csv`** — one row per plan,
one column per attribute, zero blank cells. It's generated by
`build_wide_dataset.py` from the read-only master in `input/`.

(The separate `segregate_telecom_data.py` / `telecom_datasets.xlsx` are a
legacy 3-sheet segregation deliverable and are no longer used by the chatbot.)

## Setup

1. **Install dependencies**
   ```bash
   pip install -r requirements.txt
   ```

2. **Build the dataset** (if `output/vi_plans_wide_dataset.csv` isn't there)
   ```bash
   python build_wide_dataset.py
   ```

3. **Add your Gemini API key** — get a free one at
   https://aistudio.google.com/apikey
   ```bash
   copy .env.example .env
   ```
   Then edit `.env` and set `GEMINI_API_KEY=...`
   (or set it in your shell: `set GEMINI_API_KEY=your_key` on Windows).

4. **Run the app**
   ```bash
   streamlit run app.py
   ```
   It opens in your browser at http://localhost:8501.

## What it can answer

**Anything about the plans** — there's no fixed menu of supported questions.
A single fact ("price of the 449 plan?", "does 26104439 have 5G?"), a filter
("5G plans under ₹400"), a count, a comparison, alternatives, a recommendation,
or a follow-up to the previous turn. It answers what was asked and stops.

## Checking accuracy

```bash
python -m chatbot.eval
```

Builds test cases from the current dataset and checks fact recall, price
filtering, OTT lookup, and two hallucination traps (a fake plan code and a fake
benefit). Prints a pass/fail report; exits non-zero on failure.

## Dataset columns

`build_wide_dataset.py` carries through the real plan facts (price, validity,
voice, data, SMS, OTT, circles) and adds the reference-taxonomy fields as
columns: `Video_Benefit`, `OTTS_Detail`, `Activation_ViApp` / `_Website` /
`_SCRM` / `_TAT`, `Additional_Information`, `Tagging_Enquiry` / `_Request` /
`_Complaint`, and `Base_Tariff`.

Absence is always written out (`Not Included`, `No OTT Bundled`, `No Daily Cap`,
`Not Applicable`) so no cell is ever blank or read as missing by another tool.

> Note: the activation-mode and care-tagging values are standard synthetic text
> — the source had no column for them. Everything else derives from real data.

## Quota & reliability

Google's free tier meters requests **per model per day** — and the newest
models have the smallest allowance (`gemini-3.6-flash` gives only 20/day).
Two things keep the app usable inside that:

**1. Fewer tokens per question.** The whole catalogue goes to the model on every
question, so its size drives quota use. It's sent as CSV rather than
list-of-JSON (the header is stated once instead of 58 column names × 62 plans),
and the 10 columns that are identical for every plan are hoisted out and stated
once. Same information, **~36,000 → ~14,500 tokens (-60%)**.

**2. Automatic failover.** Because each model has its own separate daily
counter, `chatbot/llm.py` walks a chain of them:

```
gemini-3.6-flash → gemini-flash-latest → gemini-3.5-flash
                 → gemini-flash-lite-latest → gemini-3.5-flash-lite
```

- a **burst 429** (small retry delay) → waits it out, retries the same model
- a **daily 429** → that model is done today, moves to the next
- a **503 "high demand"** → backs off, retries, then moves to the next model
- anything else (bad key, bad request) → raised immediately, no pointless retries

A hard 45-second ceiling per question stops an outage from hanging a rep on a
live call. When everything really is spent, the UI says so in plain language
instead of dumping a traceback.

The sidebar shows which model is actually answering and the full chain.

## Security

- The API key is read from the environment / `.env` — never hard-coded.
- `.env` is git-ignored. Don't commit your key.
- The dataset stays local; only the user's question + the catalogue context are
  sent to the Gemini API per turn.
